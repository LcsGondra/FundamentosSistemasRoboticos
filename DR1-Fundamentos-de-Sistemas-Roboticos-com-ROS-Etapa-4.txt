from rclpy.node import Node
from geometry_msgs.msg import Twist
class VelocidadePub(Node):
def __init__(self):
super().__init__('velocidade_pub')
self.pub = self.create_publisher(Twist, '/cmd_vel', 10)
self.create_timer(0.5, self.tick)   # 2 Hz
def tick(self):
msg = Twist()
msg.linear.x = 0.0
msg.angular.z = 0.5
self.pub.publish(msg)
def main(args=None):
rclpy.init(args=args)
rclpy.spin(VelocidadePub())
rclpy.shutdown()

Timers e frequência de publicação
O timer é quem controla o ritmo, não um loop manual
EXEMPLO — NÃO EXECUTAR AGORA
• create_timer(período_em_segundos, callback) chama o 
callback automaticamente nesse intervalo
• Para 2 Hz (o que o TP2 pede), o período é 1/2 = 0.5 
segundos
• Nunca use time.sleep() dentro do callback — isso bloqueia 
todo o executor
• 'ros2 topic hz /cmd_vel' deve indicar frequência próxima 
de 2.0 Hz — é assim que o TP2 valida esse requisito
Fórmula rápida
período (s) = 1 / frequência (Hz)
2 Hz → 0.5s (o valor do TP2)
10 Hz → 0.1s
0.2 Hz → 5s

import math
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy
from geometry_msgs.msg import Twist
class MonitorVelocidade (Node):
def __init__(self):
super().__ init__('monitor_velocidade ')
qos = QoSProfile(depth=10, reliability= ReliabilityPolicy.BEST_EFFORT )
self.create_subscription (Twist, '/cmd_vel', self.callback , qos)
def callback(self, msg):
v = math.sqrt(msg.linear.x **2 + msg.linear.y **2 + msg.linear.z **2)
sentido = 'horário' if msg.angular.z < 0 else 'anti -horário'
self.get_logger ().info(f'v={v:.2f} m/s, sentido={sentido}')
def main(args=None):
rclpy.init(args=args)
rclpy.spin (MonitorVelocidade ())
rclpy.shutdown ()

O que evitar dentro de um callback
• Não bloqueie: nada de time.sleep(), input() ou chamadas de rede síncronas demoradas
• Não chame rclpy.spin() de novo dentro do callback
• Cálculos simples são seguros; processamento pesado deve rodar em outra thread
• Se precisar chamar um serviço a partir de um callback, use call_async — nunca a chamada bloqueante

O que é QoS e por que importa
Quality of Service — o contrato de confiabilidade da comunicação
EXEMPLO — NÃO EXECUTAR AGORA
• Define o comportamento da comunicação sob perda de 
pacotes, reconexões e diferenças de velocidade
• Publisher e subscriber negociam QoS na descoberta —
perfis incompatíveis impedem a conexão
• O TP2 pede explicitamente BEST_EFFORT no 
monitor_velocidade — vamos entender por quê
• Configurado via QoSProfile, passado no 
create_publisher/create_subscription
Analogia
É como escolher entre carta registrada (garantida, mas 
lenta) e um anúncio de rádio (rápido, mas pode não 
chegar) — a escolha depende do que está sendo 
transmitido.

Reliability: RELIABLE vs BEST_EFFORT
Critério RELIABLE BEST_EFFORT
Garantia de entrega Sim, reenvia se perder Não, descarta silenciosamente
Latência Maior (por causa do reenvio) Menor
Cenário robótico ideal Comandos de velocidade, serviços Streaming de câmera/lidar a alta taxa

Durability: VOLATILE vs TRANSIENT_LOCAL
Critério VOLATILE TRANSIENT_LOCAL
Mensagens antigas Descartadas — só recebe o que chegar

History e Depth
Quantas mensagens ficam na fila de cada lado
EXEMPLO — NÃO EXECUTAR AGORA
• History KEEP_LAST(n): guarda só as últimas n mensagens 
(mais comum)
• History KEEP_ALL: guarda todas — cuidado com uso de 
memória
• Depth define o valor de n quando KEEP_LAST é usado
• No monitor_velocidade usamos depth=10 — o mesmo 
valor padrão do create_publisher do velocidade_pub
Valor típico
depth=10 é um bom padrão para tópicos de controle 
como /cmd_vel. Sensores de alta frequência (câmera, 
lidar) costumam usar depth menor (1-5).

Compatibilidade de QoS
O que acontece quando publisher e subscriber divergem
EXEMPLO — NÃO EXECUTAR AGORA
• RELIABLE (publisher) + BEST_EFFORT (subscriber) → 
funciona (o subscriber aceita menos garantia)
• É exatamente o caso do TP2: velocidade_pub usa o 
padrão RELIABLE, monitor_velocidade pede BEST_EFFORT 
— compatível
• BEST_EFFORT (publisher) + RELIABLE (subscriber) → 
INCOMPATÍVEL, a conexão não é estabelecida
• O ROS 2 não avisa com um erro explícito — o sintoma é 
'não chegam mensagens'
Como depurar
ros2 topic info /cmd_vel --verbose mostra o QoS de 
cada publisher e subscriber conectado — use antes de 
entregar o TP2 para confirmar que os dois nós estão 
compatíveis.

COMPETÊNCIA 2 · SERVIÇOS CLIENT/SERVER · APLICAÇÃO
Serviço em vez de tópico?
Revisão prática da decisão
• Use serviço quando a operação é pontual e você precisa 
de confirmação (ligar um modo, resetar um estado)
• Use tópico quando o dado é contínuo e perdas ocasionais 
são aceitáveis (sensores, cmd_vel)
• Serviço bloqueia o client até responder — não use para 
operações demoradas (para isso existe Ação)
Exemplo do TP2
Ligar/desligar o 'modo autônomo' de um robô é uma 
operação pontual com confirmação — por isso o TP2 
pede um serviço (modo_server), não um tópico.

import rclpy
from rclpy.node import Node
from std_srvs.srv import SetBool
class ModoServer(Node):
def __init__(self):
super().__init__('modo_server')
self.create_service(SetBool, 'modo', self.callback)
def callback(self, request, response):
if request.data:
response.message = 'Robô em modo autônomo ativado'
else:
response.message = 'Robô em modo manual ativado'
response.success = True
return response
def main(args=None):
rclpy.init(args=args)
rclpy.spin(ModoServer())
rclpy.shutdown()

Campos de resposta: success e message
O que o modo_client vai ler
EXEMPLO — NÃO EXECUTAR AGORA
• success=True/False informa objetivamente se a operação 
funcionou
• message é exatamente o texto que o TP2 pede: 'Robô em 
modo autônomo ativado' ou 'Robô em modo manual 
ativado'
• O client SEMPRE deve checar response.success antes de 
assumir sucesso
• Evite lançar exceções não tratadas dentro do callback —
isso derruba o server
Validação do TP2
'ros2 run comunicacao_ros2 modo_client -- true' deve 
imprimir exatamente 'Robô em modo autônomo 
ativado' — a string precisa bater com o que o Server 
devolve.

Executors: Single vs MultiThreaded
Quem decide a ordem em que os callbacks rodam
EXEMPLO — NÃO EXECUTAR AGORA
• SingleThreadedExecutor (padrão): processa um callback 
por vez, em sequência
• MultiThreadedExecutor: processa múltiplos callbacks em 
paralelo, em threads diferentes
• modo_server e modo_client, do jeito que construímos, 
funcionam bem com o executor padrão
• MultiThreaded só é necessário quando um mesmo nó 
precisa atender E chamar serviços ao mesmo tempo
Regra prática
Se seu nó só publica/assina tópicos ou só atende 
serviços (não os dois cruzados), o executor padrão 
single-threaded é suficiente.

COMPETÊNCIA 2 · SERVIÇOS CLIENT/SERVER · CONCEITO
Por que call_async pode travar
O problema do deadlock em executor single-threaded
EXEMPLO — NÃO EXECUTAR AGORA
Callback A
(server)
chama
Serviço B
(outro server)
Se o Callback A usa call() (síncrono/bloqueante) e espera pela resposta do Serviço B, mas o executor single-threaded só tem UMA 
thread — a mesma thread que precisaria processar a resposta de B está travada esperando dentro de A. Resultado: deadlock 
permanente.
Solução: use call_async() dentro de callbacks (como fizemos no modo_client), ou um MultiThreadedExecutor.
