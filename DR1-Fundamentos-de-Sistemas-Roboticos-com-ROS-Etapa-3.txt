O grafo computacional do ROS 2
Nós, tópicos, serviços e ações são os vértices e arestas de um grafo distribuído
• Nó (node): processo independente que executa uma 
tarefa específica (ler um sensor, planejar uma trajetória, 
publicar comandos)
• Cada nó roda isoladamente e pode estar em máquinas 
diferentes
• Os nós se conectam entre si através de tópicos, serviços e 
ações
• O conjunto de nós + conexões ativas em um instante é 
chamado de grafo computacional (computation graph)
Por que isso importa?
Todo comando de inspeção do ROS 2 (ros2 node, ros2 
topic, ros2 service) é, na prática, uma consulta a esse 
grafo em tempo real. Entender essa metáfora é a base 
para depurar qualquer sistema robótico distribuído.

Tópicos: comunicação assíncrona
Publish/Subscribe — o mecanismo mais usado no ROS 2
• Um publisher envia mensagens para um canal nomeado (o 
tópico), sem saber quem vai recebê-las
• Um ou mais subscribers recebem cada mensagem 
publicada, de forma assíncrona
• Relação muitos-para-muitos: vários publishers e vários 
subscribers podem coexistir no mesmo tópico
• No TP2, /cmd_vel vai ser exatamente esse canal: 
velocidade_pub publica, monitor_velocidade assina

monitor_
velocidade
outro nó
qualquer
/cmd_vel
O publisher não sabe quem (nem quantos) está ouvindo — é como um 
anúncio de rádio.

COMPETÊNCIA 1 · COMUNICAÇÃO E DESCOBERTA · APLICAÇÃO
Escolhendo o mecanismo certo
• "Preciso transmitir dados continuamente e não importa se alguém perde uma mensagem?" → Tópico (ex.: /cmd_vel do 
velocidade_pub)
• "Preciso de uma confirmação imediata de que uma ação pontual foi executada?" → Serviço (ex.: modo_server 
ligando/desligando um modo)
• "A tarefa demora, preciso acompanhar o progresso e talvez cancelar?" → Ação (ex.: mover um braço robótico até uma 
posição)
• Regra prática: comece sempre pelo tópico; use serviço quando precisar de confirmação síncrona; use ação só quando 
o feedback contínuo for essencial.

DDS: o middleware por trás do ROS 2
Data Distribution Service — o protocolo real de comunicação
• O ROS 2 não implementa rede do zero: ele delega toda 
comunicação a uma implementação DDS (ex.: Fast DDS, 
Cyclone DDS)
• DDS é um padrão da indústria (OMG) usado também em 
aviação, defesa e telecom
• Fornece descoberta automática, QoS configurável e 
comunicação peer -to-peer, sem um broker central
• rclpy e rclcpp são camadas que traduzem a API do ROS 2 
para chamadas DDS
Por que isso importa?
Diferente do ROS 1 (que dependia de um roscore 
central), no ROS 2 não existe ponto único de falha: se 
um nó cair, os demais continuam se comunicando 
normalmente.

Descoberta automática
Como os nós se encontram na rede sem um servidor central
• Cada nó, ao iniciar, anuncia sua presença via multicast UDP na rede local
• Os demais nós no mesmo domínio recebem esse anúncio e trocam metadados (tópicos publicados/assinados, tipos, 
QoS)
• Esse processo é contínuo: um nó que entra depois é descoberto automaticamente, sem reiniciar os outros
• Não existe um 'roscore' — a descoberta é totalmente distribuída

Visualizando o grafo com rqt_graph
Uma alternativa gráfica à inspeção via terminal
• rqt_graph desenha nós como bolhas e tópicos/serviços
como setas entre elas, em tempo real
• Útil para conferir visualmente se velocidade_pub e 
monitor_velocidade estão realmente conectados pelo
/cmd_vel

• Complementa (não substitui) a CLI — para detalhes de 
tipo e QoS, a CLI ainda é necessária
Dica
Em sistemas com dezenas de nós, comece pelo 
rqt_graph para ter a visão geral, depois use ros2 topic 
info --verbose nos tópicos específicos que precisar 
depurar.

COMPETÊNCIA 1 · COMUNICAÇÃO E DESCOBERTA · BOAS PRÁTICAS
Nomenclatura e organização do grafo
• Use nomes descritivos e em snake_case: /cmd_vel, /battery_state, não /t1 ou /dados
• Prefira namespaces a nomes compostos manualmente (/robo1/cmd_vel em vez de /robo1_cmd_vel)
• Documente o tipo de cada tópico/serviço customizado no README do pacote
• Evite nomes genéricos demais (/data, /status) que colidem entre pacotes diferentes
• Um nó, uma responsabilidade: velocidade_pub só publica, monitor_velocidade só assina

Ciclo de vida de um nó
init → spin → shutdown
FRAGMENTO — junta com o slide anterior
comunicacao_ros2/comunicacao_ros2/velocidade_pub.py
def main(args=None):
rclpy.init(args=args)
no = VelocidadePub()
rclpy.spin(no)      # bloqueia aqui
no.destroy_node()
rclpy.shutdown()
if __name__ == '__main__':
main()
spin()
rclpy.spin() entra em um loop infinito que 
processa callbacks (timers, mensagens 
recebidas) até o processo ser interrompido

Logging com get_logger()
Nunca use print() em um nó ROS 2
EXEMPLO — NÃO EXECUTAR AGORA
self.get_logger().info('mensagem normal')
self.get_logger().warn('algo suspeito')
self.get_logger().error('falha grave')
self.get_logger().debug('detalhe técnico')
Por quê?
Os logs do get_logger() incluem 
automaticamente timestamp, nome do nó e 
nível de severidade — e podem ser filtrados 
via 'ros2 run --log-level'. print() não aparece 
nesses filtros nem nos arquivos de log.

Overlay vs. underlay
Por que é preciso dar 'source' depois de cada build
EXECUTAR AGORA NO TERMINAL
• Underlay: a instalação base do ROS 2 
(/opt/ros/humble/setup.bash)
• Overlay: o seu workspace (~/tp1_ws/install/setup.bash), 
que 'empilha' sobre o underlay
• Sem dar source no overlay, o shell não enxerga o pacote 
comunicacao_ros2 que você acabou de compilar
• Cada terminal novo precisa repetir os dois source (ou 
automatizar via .bashrc)
Comando
source /opt/ros/humble/setup.bash
source ~/tp1_ws/install/setup.bash
A ordem importa: o overlay deve ser sourced depois do 
underlay.

Organização do código
• Um arquivo por nó, nomeado igual ao nó (velocidade_pub.py → nó 'velocidade_pub')
• Sempre registre o entry point no setup.py antes de tentar 'ros2 run'
• Rode 'colcon build --packages-select' após CADA alteração, mesmo pequena
• Mantenha o get_logger() como única forma de saída — nunca misture com print()
• Commite o package.xml e setup.py junto com o código — são parte do pacote
